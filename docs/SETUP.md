# QA Stock Board — 설정·배포 가이드 (5.5)

이 문서의 경로와 명령은 프로젝트 루트를 기준으로 합니다. 웹 배포물은 `dist/`, Worker 원본은 `backend/cloudflare_worker.js`, 보안 규칙 원본은 `backend/firestore.rules`입니다. 과거 설계 문서에 복사된 규칙이나 코드 조각을 배포하지 않습니다.

## 1. 배포 전

1. 구버전 HTML·Worker·현재 Firebase 규칙을 보관합니다.
2. 앱의 거래기록 → 도구 → 전체 데이터 백업을 받습니다. 구버전에서 업그레이드하는 최초 1회는 Firebase 콘솔의 데이터 또는 기존 내보내기도 함께 보관합니다.
3. `node scripts/verify.cjs`와 로컬 브라우저 검사를 실행합니다.
4. Firebase 규칙의 허용 이메일이 사용할 가족 계정과 맞는지 확인합니다.

## 2. Firestore 보안 규칙

**오직 `backend/firestore.rules` 파일 전체를 배포합니다.** 사용자 데이터는 `users/{로그인UID}/` 아래에 있습니다. 허용 이메일이어도 다른 UID의 데이터에는 접근할 수 없어야 합니다.

Google 공급자, 이메일 인증 여부, 허용 이메일, 로그인 UID 일치가 모두 필요합니다. 전체 DB에 허용 이메일의 읽기·쓰기를 주는 구버전 예시를 사용하지 마세요. 새 컬렉션도 동일 UID 규칙을 적용받습니다.

루트 `qa_*`의 구버전 데이터가 남아 있다면 자동 이관하거나 삭제하지 않습니다. 현재 사용자별 데이터 존재 여부를 확인하고 별도 백업·검증 후 이관해야 합니다.

## 3. 웹 앱

- `node scripts/build.cjs`가 생성한 `dist/`를 **통째로** 배포합니다: `index.html`, `favicon.ico`, `apple-touch-icon.png`, 그리고 **5.5부터 `vendor/firebase-10.14.1/` 폴더(스크립트 3개)**. HTML은 이 폴더를 같은 출처에서 SRI로 싣습니다 — 폴더를 빠뜨리면 로그인 화면조차 뜨지 않습니다.
- HTML `<head>`에 CSP가 들어 있습니다(인라인 스크립트는 해시로만 허용). 배포 후 로그인이 막히면 원인 확인 전까지 CSP `<meta>` 한 줄을 지워 되돌릴 수 있습니다. HTML을 손으로 고치면 해시가 맞지 않아 스크립트가 멈추므로, 항상 `src/`를 고치고 다시 빌드합니다.
- Firebase Authentication의 승인된 도메인 설정은 기존 운영 도메인을 유지합니다.
- `src/`, `tests/`, 로컬 미리보기 서버는 운영 HTML에 별도 설치하지 않습니다.
- 이 빌드에는 서비스워커·오프라인 쓰기 큐를 새로 설치하지 않습니다. 오프라인 상태를 표시하며 확인되지 않은 데이터를 최신으로 표현하지 않습니다.

## 4. Worker

- `backend/cloudflare_worker.js`(v7.0)를 기존 Worker에 배포합니다. 기존 `KRX_AUTH_KEY` Secret은 그대로 유지합니다.
- **필수** 환경변수 `ALLOWED_EMAILS` — `firestore.rules`의 `allowedEmails()`와 같은 이메일을 쉼표로. 없으면 모든 요청이 503입니다(열린 채로 동작하지 않게).
- `ALLOWED_ORIGINS` — 앱이 실제로 열리는 주소의 origin(예: `https://<계정>.github.io`)을 쉼표로. 기본값은 `https://wonjeong-dev.github.io`이며, 저장소를 옮겼다면 반드시 지정합니다. 목록에 없으면 브라우저가 응답을 읽지 못합니다.
- `AUTH_MODE=report` — 전환기용. 토큰이 없어도 통과시키고 `X-QA-Auth: fail:<사유>`만 붙입니다. 이 값을 지우면(또는 오타여도) enforce로 동작합니다.
- `KRX_SCHEME=http` — KRX가 https를 받지 않을 때만. 기본은 https입니다(미실측).
- 선택 `RATE_LIMITER` 바인딩은 **인증 뒤** 사용자 단위로 적용됩니다.
- 무인증 경로는 `OPTIONS`와 `/health`(버전만)뿐입니다. 브라우저 주소창으로 `/summary`를 열면 401이 정상입니다.
- 캐시는 인증 뒤 조회하며, 키는 허용 파라미터만으로 정규화합니다. 부분 성공·오류·진단 응답은 저장하지 않습니다.
- 앱 설정의 프록시 형식은 `https://YOUR-WORKER.workers.dev/?url={url}`입니다.
- `/summary`는 기존 `de`와 새 정규화 `deRatio`를 함께 반환하여 기존 HTML과 호환됩니다.

## 4-1. 5.5 배포 순서 (순서가 중요합니다)

1. 전체 백업을 받고, 현재 HTML·워커·규칙을 보관합니다.
2. **워커 v7.0**을 `AUTH_MODE=report`, `ALLOWED_EMAILS`, `ALLOWED_ORIGINS`와 함께 먼저 배포합니다. 구 워커의 CORS(`Allow-Headers: *`)는 `Authorization` 헤더를 허용하지 않으므로, 앱을 먼저 올리면 워커 호출이 전부 실패하고 공개 프록시로 떨어집니다(그 값은 5.5에서 저장되지 않습니다).
3. **앱 5.5**(`dist/` 전체, `vendor/` 포함)를 배포하고 로그인합니다. 🩺 자기점검의 '공개 프록시 경유'가 비어 있는지 확인합니다.
4. 하루 정도 워커 로그에서 `[qa-auth report]` 줄이 앱 요청에서 나오지 않는지 확인한 뒤 `AUTH_MODE`를 지웁니다(enforce).
5. **보안 규칙 v5.5**를 배포합니다. 구 앱(5.4)은 판정 로그에 `sat`를 쓰지 않아 새 규칙에서 저장이 거부되므로, 앱보다 먼저 올리지 않습니다.
6. `src/app.js`의 `CONST_LOG`에서 v5.5 행의 `from`을 실제 배포일로 고쳐 다시 빌드합니다.

## 5. 첫 사용 점검

- 로그인 후 계정 A/B의 종목·거래가 독립적인지 확인합니다.
- 데스크톱에서 계정 A를 연 채 다른 탭에서 로그아웃하면 기존 페이지도 비워지고 다시 로그인 화면으로 초기화되는지 확인합니다.
- 종목 상세에서 기존 수동 부채비율의 단위를 선택합니다.
- 거래내역에서 당일 매수·매도가 섞인 기록의 체결순번을 정리합니다. 단순 입력순번을 실제 체결순서로 가정하지 않습니다.
- 같은 종류의 실계좌가 여러 개면 별칭으로 분리합니다. 자동 일괄 이관은 하지 않습니다.
- 새 검증 로그는 브라우저를 열고 데이터가 준비된 날부터 쌓입니다. 앱을 닫은 날의 자동 수집 기능은 포함하지 않습니다.

## 6. 백업·복구

전체 백업에는 거래·환전·분할·유상증자·관심종목·설정·상장주식수 기준·캐시·판정 로그·지수 캐시·사전 고정 검증 보관본(`qa_prereg`)을 담습니다. 현재 로그인 UID와 다른 백업은 거부합니다.

5.5부터 **판정 로그는 복구하지 않습니다** — 보안 규칙이 판정 로그의 생성을 '그날의 서버 시각'으로만 허용하기 때문입니다(과거 판정의 수정·백데이팅을 막는 것이 목적). 필요하면 Firebase 콘솔에서 관리합니다. 복구 전 거래 행의 필수값(일자·구분·시장·단가·수량·코드 또는 종목명)을 검사하고, 맞지 않는 행이 있으면 복구를 시작하지 않습니다.

복구 파일 선택 → 문서 수·충돌 미리보기 → 확인 체크 → 현재 백업 다운로드 → 같은 ID 덮어쓰기 순서입니다. 백업에 없는 현재 문서는 삭제하지 않습니다. 여러 배치에 걸쳐 수행되므로 중간 실패 시 일부만 반영될 수 있으며, 같은 파일로 재시도할 수 있습니다. 다른 기기에서는 동시에 편집하지 마세요.

## 7. 되돌리기

배포 HTML과 Worker를 보관한 이전 버전으로 되돌립니다. v5.2 데이터는 임의로 삭제하지 않습니다. 새 규칙·계좌 별칭·미확정 손익 처리에 맞지 않는 구버전으로 되돌리면 표시가 달라질 수 있으므로, 데이터 복구는 별도의 미리보기와 검증을 거칩니다.
